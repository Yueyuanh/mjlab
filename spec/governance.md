# 规范维护与治理

## 约束等级

- **必须**：缺失会破坏安全性、可复现性或产物可追溯性。例外必须写入实验 README。
- **应当**：默认执行；不执行时记录原因和替代证据。
- **可以**：推荐做法，可按任务特点选择。

## 适用原则

1. 本规范面向新实验和正在继续的实验，不追溯性重排所有历史产物。
2. 更具体的主题规范优先于一般规范；实验级例外只对该实验有效。
3. 用户在当前任务中的明确要求优先。Agent 不得用本规范扩大任务范围或执行未授权操作。
4. 历史报告是事实记录，不因新规范而改写；需要更正时追加勘误和日期。
5. `spec/` 是流程规范的单一入口。命令示例仍以 CLI `--help` 和当前源码为最终依据。

## 修改流程

修改规范时应当：

1. 说明触发修改的真实问题或实验经验；
2. 标出受影响主题，以及它是新增、收紧、放宽还是澄清；
3. 同步更新 `spec/README.md` 索引和 `agent-defaults.md` 路由（若相关）；
4. 检查 `AGENTS.md`、`CLAUDE.md`、`TrainSpec.md` 是否出现实质冲突；
5. 对自动化可验证的强制项，优先增加测试或校验脚本，而不是只写文字。

规范版本采用轻量版本号：

- patch：措辞澄清，不改变行为；
- minor：新增检查项或主题；
- major：改变目录、模型晋级或评估口径等现有契约。

当前 `v0.2-draft` 是共同制定阶段。`v0.2` 将日志目录改为阶段优先、run 内聚，并统一 full 自动评估
和最终视频规格。条目经过至少一次新实验验证后再提升为 `v1.0`。

## 例外记录

工具要求保留原生扁平目录、硬件暂不可用或旧模型无法完整复现时，不应伪造合规状态。
在实验 README 中记录：

- 偏离了哪条规范；
- 原因和影响；
- 已采取的替代验证；
- 后续是否需要补齐。

例外不能省略 checkpoint 身份、有效配置、代码来源和评估协议这四类核心证据。
