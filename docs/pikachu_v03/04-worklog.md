## 2026-10-01 · r01 定性：**策略在站桩**，找到两个独立缺陷（已修，待复跑验证）

### 怎么定性的

看板上的 `track_linear_velocity = 1.4/2.0` 是**二义**的：命令幅度平均
~0.25 m/s 时，「站着不动」的跟踪误差本身就只有 0.25 左右，exp 项天然能拿到
0.7+。光看奖励分不出「走得不错」和「站着不动」。

所以新写了 `scripts/eval_v03_velocity.py`：把命令**固定成档位**，跑 8 s，
量 base 在**世界系的净位移**除以时间，与命令对比。

> ⚠️ 用净位移而不是瞬时速度 —— 步态瞬时速度有周期性起伏，均值可信单帧不可信
> （记忆 `amp-v4-behavior-direction`）。

对 `model_500.pt`（r01 中途存档）逐档评测：

| stand | 0.00 | 0.00 | 0.00 | 0.001 | 0.000 | 0.001 | — | -0.6 | 3.0 | 0 | 0.00 | 7.00 |

**五个档位实测速度全是 0.001 m/s，单脚支撑占比 0.00 —— 一次脚都没抬过。**
姿态倒是完美（roll -0.6°、pitch 3.0°、零终止）。

> 📌 **迈步判据用「单脚支撑占比」，不要用「接触翻转次数」当步频**：
> 胶囊脚底在软接触下 `found` 会抖动，站着不动也能翻出 3~4 Hz 的假步频
> （实测踩过）。单脚支撑占比没这个毛病：真迈步稳定在 0.3~0.6，站桩接近 0。

### 根因：两个**互相独立**的缺陷

**缺陷 1 —— track 奖励的 std 没随命令范围缩放。**

`make_velocity_env_cfg` 给的默认 std（lin `√0.25 = 0.5`、ang `√0.5 = 0.707`）
是配 G1 那种 ±3 m/s 大命令的。v03 的命令收窄到 lin ±0.5 / ang ±0.3 之后：

```
站桩误差 mean|cmd| ≈ 0.29 m/s
exp(-0.29² / 0.5²) = 0.72     →  站桩白拿 72% 的跟踪分
```

梯度压力直接消失，策略落向「站着不动」这个鞍点。

> 这**不是新坑** —— AMP 侧踩过一模一样的，见记忆
> `amp-track-std-must-match-command`（Pikachu 取 lin 0.12 / ang 0.25）。

**缺陷 2 —— `alternating_feet_air_time` 在「从不抬脚」时是**死梯度**。**

翻它的实现（`tasks/velocity/mdp/rewards.py`）：它只在**落地瞬间**
（`first_contact & has_other_support`）给分。策略一次脚都不抬 → 没有落地事件
→ 该项恒为 0，**梯度也为 0**。光靠它推不出第一步（r01 实测 `air_time`
只有 +0.0016）。同文件的 `feet_air_time` 是**每步**给分（
`threshold_min < current_air_time < threshold_max` 就计分），有活梯度。

### 修复（`env_cfgs.py`）

1. `track_linear_velocity.std`: 0.5 → **0.20**；
   `track_angular_velocity.std`: 0.707 → **0.25**
   （收到命令上限量级：lin 站桩只剩 0.13 分，ang 站桩 0.70）。
2. 抬脚奖励拆成两项，**缺一不可**：
   - `air_time` = `feet_air_time`（每步给分，weight 1.0）→ 把策略推离站桩鞍点
   - `alternating_air_time` = `alternating_feet_air_time`（落地质量，weight 3.0）
     → 它不能靠「双脚一起腾空」刷分，负责把步态收成真交替步
3. `pose.std_walking` 放宽：`hip_pitch`/`knee_up` 0.5、`ankle` 0.45
   （原值把正常迈步摆幅当误差罚，策略为保 pose 分不敢抬腿）；
   `hip_roll`/`hip_yaw` 保持 0.15 收着。

### ⚠️ 重要：`Episode_Reward/track_*` **本身会骗人**，别拿它当进度指标

读实现（`tasks/velocity/mdp/rewards.py`）：

```python
lin_vel_error = |cmd_xy − actual_xy|² + actual_vz²
reward = exp(-lin_vel_error / std²)        # weight 2.0
```

奖励是 `exp(−误差²)` 的**逐帧均值**，而 `error_vel_xy` 是**时均误差**。
`exp(−x²)` 在 |x| > 1/√2 区间是凸的，由 Jensen 不等式，
「一半时间跟得准、一半时间跟得烂」也能刷出高分：

| 场景 | mean\|err\| | mean(exp(−err²/0.04)) |
|---|---|---|
| 恒定 err = 0.17 | 0.17 | 0.50 |
| err 在 0.05 / 0.90 间各半 | **0.475** | **≈0.47** |

**所以 `track_linear_velocity = 1.00` 对应的等效误差只有 ~0.17，
而 `error_vel_xy` 报的是 0.42。两个数不矛盾，但只有后者诚实。**

反过来，这个公式**反过来验证了 r01 的站桩诊断**：
站桩时 err ≈ mean\|cmd\| = 0.29、默认 std = 0.5

```
2 · exp(−0.29² / 0.25) = 1.43
```

而 **r01 实测 `track_linear_velocity` = 1.392 ~ 1.453** —— 分毫不差。
这就是「站桩白拿 72% 跟踪分」那句话的精确版本。

**纪律**：判断「在走还是在站」，只看 `Metrics/twist/error_vel_xy` 的**趋势**
和 `eval_v03_velocity.py` 的**净位移**，不看奖励分。

## 2026-10-01 · ⚠️ 抓到一个极隐蔽的 bug：命令固定**根本没生效**

### 症状

输出**一模一样**：

```

fwd      0.40  0.00  0.00 | -0.062  0.033  0.232 | 0.18  5.2  -0.9  0  0.15

lat      0.00  0.25  0.00 | -0.062  0.033  0.232 | 0.28  5.2  -0.9  0  0.15
turn     0.00  0.00  0.30 | -0.062  0.033  0.232 |  nan  5.2  -0.9  0  0.15
```

**这个形态极具误导性** —— 看起来像「策略完全忽略命令」，实际上是我把命令
写进去的那一步失败了。

### 排查路径（值得记，因为每一步的结论都曾看起来"没问题"）

1. 先怀疑 `ranges` 是只读属性 → 打印 `type(term.cfg.ranges)`，是普通
   dataclass，赋值能读回来 ✓
2. 怀疑 env 拿的不是我改的那个对象 → 打印 `id()`，`term.cfg is t` → **True** ✓
3. 怀疑 `_resample_command` 被子类重写 → 打印 `__qualname__`，就是
   `UniformVelocityCommand._resample_command`，且全文只用 `self.cfg.ranges` ✓
4. **打桩**：包一层 `_resample_command`，在**调用时刻**打印 `self.cfg.ranges`

```
打桩前 term.cfg.ranges.lin_vel_x = (0.4, 0.4)
>>> INSIDE self.cfg.ranges.lin_vel_x = (-0.4, 0.5)   ← 变回默认值了！
```

### 根因

`cfg.curriculum["command_vel"]`（`tasks/velocity/mdp/curriculums.py::commands_vel`）
**每一步都用 stage 配置覆写 `cfg.ranges.*`**：

```python
for stage in velocity_stages:
    if env.common_step_counter >= stage["step"]:
        cfg.ranges.lin_vel_x = stage["lin_vel_x"]   # ← 直接写
```

stage 0 的 `step=0` **恒满足**，所以在第一次 `_resample_command` 之前，
我构造 env 前设的 `(vx, vx)` 就被改回 `(-0.4, 0.5)`。
五个档位于是全都用同一个默认范围抽样（seed 固定 → 同一个命令
`[0.072, -0.121, -0.072]`），结果当然一模一样。

### 修复

`eval_v03_velocity.py` 和 `record_v03_video.py` 里都要加：

```python
cfg.curriculum.pop("command_vel", None)
```

修完验证：

```
设定 vx=+0.40 -> env 命令 = [0.4, 0.0, 0.0]
设定 vx=-0.30 -> env 命令 = [-0.3, 0.0, 0.0]
设定 vx=+0.00 -> env 命令 = [0.0, 0.0, 0.0]
```

### 连带影响

**r01 那张「五档全 0.001 m/s」的表，命令列是错的** —— 那五档实际跑的都是
同一个命令 `[0.072, -0.121, -0.072]`（vx = +0.072，不是我写的 0.40）。
但**结论不受影响**：机器人被命令前进 0.072 m/s，实测 0.001 m/s，
依然是「一动不动」。只是「跟踪比 0.00」的分母得改成 0.072。
修复后已重跑 r01 基线，见下一节。

### ⚠️ 修正：能见到 yaw 命令的环境不是 25%，是 **6.79%**

前面写「r02 用 0.25×3 = 0.75，只剩 25% 的环境练转向」—— **这个数是错的**。
`1 − 桶总量` 只是第一步，还要连乘两件事：

```python
self.is_heading_env[env_ids] = r.uniform_(0.0, 1.0) <= self.cfg.rel_heading_envs  # 0.3
...
directional = is_forward | is_backward | is_lateral
self.is_heading_env[env_ids] &= ~directional        # ← 方向桶被踢出 heading
...
# _update_command 的最后一步：
self.vel_command_b[standing_env_ids, :] = 0.0       # ← standing 把整个命令清零
```

所以：

```
P(见过 yaw) = [ rel_heading_envs × (1 − 桶总量) ] × (1 − rel_standing_envs)
```

**只有 heading 环境会拿到非零的 `ang_vel_z`** —— 方向桶把它置 0，
standing 环境每步把整个命令清零，两个都轮不到。

| 轮次 | 桶总量 | heading | standing | 见过 yaw 的环境 |
|---|---|---|---|---|
| r01 / r02 | 0.75 | 0.3 | 0.1 | **6.79%**（139 / 2048） |
| r03 | 0.50 | 0.3 | 0.1 | **13.49%**（276 / 2048） |
| r04 预案 | 0.50 | **0.6** | **0.05** | **28.55%**（585 / 2048） |

（用 2×10⁶ 次采样模拟确认，不是纸面估算。）

**这条把「完全不会转」解释圆了**：`track_angular_velocity` 权重 2.0，
但只有 6.79% 的环境因它产生非零梯度 → 在平均奖励里的最大贡献
`2.0 × 0.068 = 0.14`，而 `track_linear_velocity` 是**全部**环境贡献的 2.0。
**信号弱 15 倍**，策略忽略 yaw 是理性的 —— 不是「学不会」，是「不值得学」。

r03 把暴露面翻倍到 13.49%。同时它还有两个独立杠杆（ang std 0.25→0.40
使 err=0.5 处梯度 ×4.5；pose 不再罚 hip_yaw），三者相乘。
**若 r03 终评转向仍不达标，r04 直接动暴露面**（上面第三行）。

### 又排除两个嫌疑

| 嫌疑 | 结论 |
|---|---|
| `body_ang_vel`（权重 −0.05）会不会罚转向？ | **不会**。`rewards.py::body_angular_velocity_penalty` 里 `ang_vel_xy = ang_vel[:, :2]  # Don't penalize z-angular velocity.` 明确排除 z 轴 |
| `angular_momentum`（权重 −0.02）罚全向量模长、含 z，会不会罚转向？ | **量级可忽略**。转身时 `L_z ≈ I·ω ≈ 0.02 × 0.3 = 0.006`，`L² × 0.02 ≈ 7e-7`，相对 `track_angular` 的 2.0 是噪声 |

### ⚠️ 修正：`单脚支撑` 这个指标一开始就量错了对象

旧代码是 `contact.data.found[0].sum() == 1`，我以为是「只有一只脚着地」。
写探针脚本打印实际形状才发现：

```
found.shape = (2, 2)          # (num_envs, slot)
found[0]    = [10.0, 10.0]    # 左脚子树 10 个接触点、右脚子树 10 个
found[0].sum() = 20.0         # ← 永远不等于 1
```

`slot` 是按 `primary` 正则匹配到的 body 逐个排的，`^(left|right)_ankle_link$`
匹配 2 个 body → 2 个 slot，**值是子树里的接触点数，不是脚数**。
`sum() == 1` 实际是「全身恰好只有 1 个接触点」，跟单脚支撑是两回事。

正确的判据是按 slot 判 `> 0` 再数：

```python
n_feet.append(int((contact.data.found[0] > 0).sum()))
```

3.46 → **1.97**，后者才符合语义）。**教训：用传感器前先打印它的形状和量纲，
不要从字段名猜。**

## 2026-10-01 · ⚠️ 关于「转向」：我前后两次评测**都问错了问题**

这是本次最值得记的一条 —— 我两次都差点给出错误结论。

### 错法一：拿恒定角速度去测（`eval_v03_velocity.py --clips turn`）

该档给的是**恒定** `ang_vel_z = 0.30`。但训练配置是
`heading_command=True`：

```python
# velocity_command.py::_update_command
ang_vel_z = clip(heading_control_stiffness(0.5) × heading_error, -0.3, 0.3)
```

即训练里策略学的是「**转到目标朝向就停**」的**位置**任务，
**从来没见过「一直转」这种命令**。恒定角速度是分布外输入，
测出来的 0.033 不能解释为「不会转」。

### 错法二：测「原地转」，但训练里根本没有原地转的环境

改用训练的语义（给目标朝向）之后，第一版仍然测出「r04 转错方向 -105°」。
排查发现是**测试自己的 bug**：`velocity_env_cfg` 的 `reset_base` 把初始
yaw 随机化在 **(-π, π)**：

```python
"pose_range": {"x": (-0.5, 0.5), "y": (-0.5, 0.5), "z": (0.01, 0.05),
               "yaw": (-3.14, 3.14)},   # ← 初始朝向是随机的
```

而 `ranges.heading` 是**世界系绝对朝向**，不是相对量。两者一叠加，
「转过多少度」量的其实是「从随机初始朝向转到 +90°」，符号自然是随机的。
修法：把 `pose_range["yaw"]` 钉成 `(0, 0)`，并且**用 env 自己算的
`cmd_term.heading_error` 判收敛**，不要自己拿 `yaw0 + dpsi` 推。

### 修好之后（`scripts/eval_v03_turn.py`）

| 场景 | 目标 | r02@2500 收敛 | r04@29999 收敛 | r04 残留 | r04 到位步 |
|---|---|---|---|---|---|
| `turn_only`（vx=0，原地转 90°） | 90° | 0.06 | **0.18** | 73.7° | 未到位 |
| **`walk_turn`（vx=0.30，边走边转 90°）** | 90° | 0.09 | **0.98** | **1.8°** | **276 步（5.5 s）** |
| `turn_180`（原地转 180°） | 180° | 0.03 | 0.63 | 65.8° | 未到位 |

（收敛 = 1 − 残留/初始误差；1.0 = 完全到位，0 = 一点没动。）

**结论彻底翻转**：

- **r04 会转向 —— 而且转得很好，但只在「边走边转」时**。
  走 0.30 m/s 的同时转 90°，5.5 秒到位、残留 1.8°、收敛 0.98。
  这正是训练里 heading 环境的**唯一形态**（heading 环境同时抽随机线速度）。
- **原地转仍然不会**（收敛 0.18），因为**训练里从来没有「纯转向」环境** ——
  方向桶把 `ang_vel_z` 强制置 0，heading 环境又总是带线速度命令。
  这是设计缺口，不是策略无能。
- r02 在两个场景都是 0.03~0.09（乱转），r04 相对 r02 是**质的改善**。

**要真正拿到「原地转」能力，正确做法是加一个纯转向桶**
（`lin=0` 且 `ang≠0` 的环境，比如占 15%）。当前 `UniformVelocityCommand`
没有这个桶，需要自己加 —— 这是 r05 的候选工作，本次不做。

> **纪律**：测一个能力之前，先确认**训练分布里有没有这种输入**。
> 拿分布外的命令去测，得到的低分是评测的错，不是策略的错。
> 我这次连续犯了两次，两次的结论都写反了。

## 2026-10-08 · 补：把模型转换期的一个错误归因改回来（坑 5）

收尾整理记录库时发现 `scripts/diag_v03_stability.py` 一直**没进库**（当时写完
就搁下了），而且它的 docstring 写的是一条**我没验证过、事后看是错的**结论：
「源模型本身在 `mj_step` 下发散，~5 步内 QACC NaN」。

重跑证伪：

- 源模型（base 焊死在世界、无执行器）**开重力 / 关重力都能稳跑 2000 步**，
  `max|qvel| = 2.2e-2`。它根本不发散。
- 唯一不稳的组合是**刚性 `position` 执行器 + 显式 `euler` 积分**。根因是
  踝关节的等效惯量只有 **9.21e-5**（`mj_fullM` 对角元，比 hip_pitch 的 1.80e-2
  小两个数量级），kp=150 时第 ~21 步就报
  `Nan, Inf or huge value in QACC at DOF 5`（DOF 5 = `right_ankle_joint`）。
- **救活它的是积分器，不是 `armature`**。分离两者：

  | 积分器 | armature | `max\|qvel\|` |
  |---|---|---|
  | `euler` | 无 | 3.11e+00 |
  | `euler` | +J3507 | 9.80e+00（**更差**） |
  | `implicitfast` | 无 | 6.3e-11 |
  | `implicitfast` | +J3507 | 3.1e-11 |

  mjlab 默认就是 `implicitfast`（`src/mjlab/sim/sim.py:103`），v03 任务没覆盖它
  —— **这个坑在训练里一直是被默认值挡掉的**，我从没真正踩到，却在文档里
  写了一条错的归因。

`armature` 的真实作用是**物理保真度**：`ARMATURE_J3507 = 6.69e-6 × 21² = 2.95e-3`，
是踝关节连杆惯量的 **32 倍**（真机上转子反射惯量本来就该主导这个关节），
刚度 `kp` 也是从它按 `STIFFNESS = ARMATURE × ω²` 反推的。

**改动**：`diag_v03_stability.py` 加了一组「euler × implicitfast」对照
（`trial()` 新增 `integrator=` 参数），让结论能被脚本本身复现而不是靠我敲的
一次性命令；docstring 改成正确结论并保留原错误假设作为教训；脚本进库。
详细写入 [01-model-conversion.md](01-model-conversion.md) 坑 5。

> 教训跟 §5.8 那次是同一个：**先跑最小复现，再写归因**。
> 这次错得更隐蔽 —— 错误结论从没被现实反驳过，因为真正生效的是别人设的默认值。

## 2026-10-08 · r05：站姿横向开度（双脚挨太近）

**用户反馈**：全向行走已经能用，但**静止站立时双脚挨太近**，没有按默认姿态站，
问能不能加一个「双脚横向距离」的奖励。

### 先量，再改

写 `scripts/measure_v03_stance.py`（分档量间距 + 各关节相对默认姿态的偏差）。
量出来两件事，第一件在意料之中，第二件不是：

**① 确实很窄，而且不只站立窄**（默认 keyframe 是 20.0 cm）：

| 档位 | 间距均值 | min | max | 比默认窄 |
|---|---|---|---|---|
| `stand` | 9.23 cm | 8.30 | 19.15 | 10.77 cm |
| `fwd` | 9.67 cm | 8.82 | 19.24 | 10.33 cm |
| `back` | 9.29 cm | 7.05 | 19.52 | 10.71 cm |
| `lat` | 12.94 cm | 10.04 | 19.63 | 7.06 cm |
| `turn` | 9.67 cm | 8.78 | 19.08 | 10.33 cm |

（`max` 那一列都接近 20 cm，是 reset 后第一步还没被策略改动的姿态。）

**② 两个 `hip_roll` 在所有档位都顶在硬限位上**：

| 档位 | right_hip_roll | left_hip_roll | 限位 |
|---|---|---|---|
| stand | **+0.2539** | **−0.2605** | ±0.26 |
| fwd | +0.2527 | −0.2602 | ±0.26 |
| back | +0.2150 | −0.2504 | ±0.26 |
| lat | +0.1924 | −0.1683 | ±0.26 |
| turn | +0.2537 | −0.2620 | ±0.26 |

策略是**主动把髋内滚到极限**去并脚的，不是碰巧站窄。

### 根因：`pose` 奖励饱和了，不是权重不够

第一反应是「把 `pose` 的 `std_standing` 收紧一点」。**这是反效果的。**

`variable_posture` 是 `exp(-mean(err²/std²))`，站立档 `std_standing = 0.05`：

```
hip_roll 偏差 0.254 →  (0.254 / 0.05)² = 25.8  →  exp(-25.8) ≈ 0
```

**这项在站立时早就饱和了**，不管腿并得更窄还是张回正常都停在 0 附近，
梯度归零 —— 策略早就不看它。收紧 std 只会让它**更早**饱和。

（顺带说明为什么 `dof_pos_limits` 也没拦住：它罚的是「超限」，而策略停在
限位内侧 0.006 rad，刚好不触发。）

### 改法：无界二次罚

新增 `feet_lateral_distance`（`velocity/mdp/rewards.py`），weight **−0.25**、
target **0.20 m**、std **0.05**：

```
error = (|Δy_foot| − 0.20) / 0.05        # 无界
reward = −0.25 × error²
```

量级核算：站立时偏差 10.8 cm → `4.67 × (−0.25) = −1.17`，与 `pose`（权重 1.0）
同量级，压得住；步态内间距自然波动 std 仅 ~1 cm → 只罚 ~0.04，不干扰迈步。

三个实现细节：

1. **base heading 系量，不是世界系**。世界系 y 间距随 yaw 按 `cos` 缩水，
   机器人转到侧向时读数假性接近 0，奖励自己就失效了。
2. **`|Δy|` 而非有符号差**，不依赖 site 解析顺序（`find_sites` 默认按模型顺序）。
3. **不加命令门控**，因为每一档都窄，不是站立特有的。

冒烟验证：零动作 20 步，`Metrics/foot_separation = 19.96 cm`（期望 20.00），
惩罚 ≈0 —— 公式和坐标系都对。

### 一条一般教训

> `exp(-err²/std²)` 形式的奖励**在误差大时是死的**。
> 它适合「跟踪」（最优解在 0 误差，策略总在附近工作），
> 不适合「约束」—— 约束被违反得越狠，奖励越早饱和、梯度越是消失，
> 策略实际上获得了「随便违反」的自由。
> 约束类项要用**无界罚**。

这跟 r01 那个坑是同一枚硬币的两面：r01 是 `exp` 的 **std 太宽**（站桩白拿
0.72 分，没有梯度推动），这次是 **std 太紧**（一偏离就饱和到 0，同样没有梯度）。
**两头都会死，`exp` 只在中间一段是活的。**

## 2026-10-08 · 录像「看不清」：是取景，不是分辨率

r05 训练中（iter 5355/30000），用户反馈录像**压根看不清效果**，要求提到 720P、
相机跟随机器人、5 秒。

### 先纠正一个前提

录像**一直就是 1280×720 @ 50 fps**，分辨率没问题。真正的毛病是相机：

```
ViewerConfig.origin_type 默认 AUTO
  -> offscreen_renderer.py::_get_camera_body_id
       对 AUTO 和 WORLD 都 return -1   # 当自由相机
  -> camera 钉在 lookat=(0,0,0), distance=5.0, elevation=-45
```

也就是说：**`AUTO` 不是「自动跟踪」，是「不动」**。`env_cfgs.py` 里早就写了
`cfg.viewer.body_name = TORSO_BODY`，但 `body_name` 只有 `ASSET_BODY` 才读，
`AUTO` 下等于没写 —— 这行配置给了「相机已经在跟机器人」的错觉。

### 量化：投影出来量，不靠肉眼猜

不能开仿真（训练在跑，内存只剩 2 GB），于是只用 `mjv_updateCamera` 做纯运动学
投影：不建 GL 上下文、不步进物理，几十 MB。把默认站姿的 mesh **真实顶点**
（`mesh_vert`，不是 `geom_aabb`）变换到世界系，再手工投到 1280×720：

| 相机 | 占画面高 | 占画面宽 |
|---|---|---|
| 旧：自由相机 `d=5.0, el=-45` | **12%** | **2%** |
| 新：`ASSET_ROOT d=1.1, el=-15`（side） | **58%** | 10% |
| 新：`d=0.9, el=-15`（front） | **64%** | 29% |

12% × 2% 就是「看不清」的全部解释；而且相机不动，0.4 m/s 走 6 s = 2.4 m
就飘出画面中心。

> ⚠️ 量的时候先用了 `geom_aabb`，它给的是 geom **局部系**的包围盒；hip 的 mesh
> 在模型里转了 35°，把局部盒的 8 个角转到世界系再取 AABB 会**放大** ——
> 量出机器人宽 0.458 m，真实只有 0.362 m。要准必须用顶点。

### 换成 tracking 相机，实测两件事

```python
env_cfg.viewer.origin_type = ViewerConfig.OriginType.ASSET_ROOT
```

1. **跟的是整机质心**：`camera.lookat` 与 `data.subtree_com[root_body_id]`
   逐位相等（都是 `[-0.0248, 0, 0.2424]`），不是 `xpos`。走路时画面平滑，
   不会被上下起伏带着抖。
2. **只跟位置、不跟朝向**：把机器人平移 2 m 再绕 z 转 90° 后，
   `scn.camera[0].forward` 一字未变（仍是 `[0, 0.9397, -0.342]`）。
   所以 `turn` 档看到的是**机器人原地转身**，而不是整个世界在转 ——
   这点如果不实测，很容易假设反了。

### 顺带发现：`side` 档看不见这次要验证的东西

r05 的全部意义是**双脚横向开度**，而侧视看到的是脚的**前后深度**，左右间距
完全被遮挡。所以加了 `--views {side,front,three_quarter}`，`front` 档是唯一
能读出开度的视角。**录完 r05 必须补一趟 front。**

同时：默认时长 6 s → **5 s**（250 帧），文件名加取景档
`{档位}__{取景}__{tag}.mp4`。一个 `(档位, 取景)` 组合建一个 env ——
相机在 `OffscreenRenderer.__init__` 里一次定死，换取景只能重建 env。

### 又一条一般教训

> **默认值会掩盖你的归因。** 这已经是本任务第二次栽在同一个模式上：
> 坑 5 是 mjlab 默认的 `implicitfast` 积分器掩盖了源模型的稳定性问题；
> 这次是 `ViewerConfig` 默认的 `AUTO` 掩盖了「相机根本没跟踪」。
> 两次都是**默认值恰好让错误的表现看起来像另一回事**。
> 读配置默认值要读**消费它的那段代码**，不能只读字段名 ——
> `origin_type: OriginType = OriginType.AUTO` 里的 `AUTO` 长得就像「自动跟踪」。

## 2026-10-09 · r05 的取舍：开度修好了，动态垮了 —— 因为那一项没有门控

### 先量化症状（用户口径：「r4 动态好但站得近，r5 张开了但动态不好」）

r05 训到 15320/30000 迭代手动停（SIGINT）。停之前**逐项**比了 r04@29999 的
最终标量 —— 关键是别只看 `Train/mean_reward`，它俩只差 1.75（65.91 vs 64.16），
看起来「差不多」，但底下是**换过的**：

| 指标 | r04 | r05 | |
|---|---|---|---|
| `Episode_Reward/track_linear_velocity` | 0.7206 | **0.3845** | ↓47% |
| `Metrics/twist/error_vel_xy` | 0.6345 | **1.0610** | ↑67% |
| `Metrics/twist/error_vel_x` | 0.2961 | **0.6339** | ↑114% |
| `Metrics/twist/error_vel_y` | 0.4960 | **0.7070** | ↑42% |
| `Episode_Reward/track_angular_velocity` | 0.8270 | **1.1101** | ↑34% |
| `Metrics/twist/error_vel_yaw` | 0.7658 | **0.3903** | ↓49% |
| `Episode_Reward/alternating_air_time` | 0.0910 | **0.1548** | ↑70% |

读法：**抬脚奖励涨了 70%，线速度跟踪掉了一半** —— 脚抬得很勤，净位移却没了。
这就是「原地踏步」。而且它**拿线速度换了角速度**：只剩原地转是好的
（`error_vel_yaw` 几乎减半）。`error_vel_y` 涨最凶也不意外 ——
`feet_lateral_distance` 量的就是 Δy，被罚得最直接。

### 站姿确实修好了（所以机制没错，是范围错了）

`scripts/measure_v03_stance.py`，站立档，base 系 y：

| | 站立双脚间距 | 比默认（20.00 cm）窄 |
|---|---|---|
| 默认 keyframe | 20.00 cm | — |
| **r04**@29999 | **9.23 cm** | 10.77 cm |
| **r05**@15000 | **16.41 cm** | 3.59 cm |

关节偏差直接点出根因：r04 站立时 `right_hip_roll **+0.2539**` /
`left_hip_roll **−0.2605**` —— **两个髋侧摆都被顶到 ±0.26 限位上**。
「双脚并拢」不是默认姿态没生效，是策略**主动把髋侧摆拧到极限**换来的。
r05 把左腿松回了（−0.0612），右腿还在限位上。

所以 r05 的机制是对的（9.23 → 16.41，+78%），**坏在它没有门控**。

### 根因：那一项是**无条件**生效的

原实现对**每一个 env、每一步**都算 `(‖Δy‖ − 0.20)² / 0.05²`，与命令无关。
而走路时：

- 摆动腿必须从身体正下方过，双脚本来就**必然**要收拢；
- `hip_roll` 不只是站姿执行器，还是**侧向平衡和转向**的执行器。

一个恒定把 `hip_roll` 往外推的力，和步态是**直接对撞**的。策略的出路是
「僵硬化」—— 见上表的原地踏步。

> **被推翻的原话**（就写在 `env_cfgs.py` 里，已就地标注）：
> 「步态内的自然波动 std 只有 ~1 cm → 该项只罚 ~0.04，不干扰正常迈步」。
> 这句话只看了「双脚并拢」这一个自由度，**漏掉了它同时在推 `hip_roll`**。
> 又一次「只看被罚的那个量，没看它借道哪个执行器」。

### r06 设计：门控 + 从 r04 热启动

两处改动，都直接对着上面的根因：

1. **`feet_lateral_distance` 加命令门控**（`command_name="twist"`,
   `command_threshold=0.1`）。命令范数用 `‖v_xy‖ + |wz|`，与
   `feet_flight_time` 同一套 —— 但**方向相反**：那里命令**开启**代价，
   这里命令**关闭**代价（站着才罚）。
   门控后走路 env 的这一项**恒为 0**，与「压根没加这一项」逐位等价。
   实测（64 env）`Metrics/stance_gate_frac = 0.0312`，正是
   `rel_standing_envs=0.05` 那批。
2. **从 `r04/model_29999.pt` 热启动** —— 字面意义的「在 r4 的基础上」。
   r04 的步态已经是对的，只需要把**站立**那一小块姿态挪一挪。

关于热启动的两个细节：

- `train.py` 的 `runner.load()` **不传 `load_cfg`**，即默认
  `{actor, critic, optimizer, iteration, rnd}` **全载**。所以优化器状态和
  迭代计数都恢复：`current_learning_iteration = 29999`，
  `learn(N)` 跑的是 `range(29999, 29999+N)`。
  **`--agent.max_iterations` 要填「还要再训多少轮」，不是总数。**
- 顺带把学习率也带过来了：`schedule="adaptive"`（KL 自适应），r04 末端
  实测已经掉到 **1e-4**（初值 1e-3）。微调正需要这种保守步长 ——
  若**不**载优化器，LR 会回到 1e-3，十倍步长很容易把 r04 的步态打散。

一个**没做**的旋钮，留作 r07 候选：`rel_standing_envs` 0.05 → 0.10。
门控后它是唯一携带该项的 env，值得多给样本（代价是 yaw 暴露面
23.75% → 22.5%，可忽略）。r06 先不动它，是为了**保持归因干净** ——
这轮只改一个东西。

  「朝向误差 × 刚度」压出来的角速度，只有放在 base 系才和
  `ang_vel_b[:, 2]` 可比 —— 这与 `UniformVelocityCommand._update_metrics`
  的口径逐字一致，误差可以直接相减，不需要任何旋转。

### 补记：`model_34999.pt` 是一根软链（它装的是 34998）

**踩坑现场**：r06 测试跑的 `--agent.max_iterations 5000`，从 29999 起算，
`learn(N)` 执行的是 `range(start, start + N)`，也就是 **29999 … 34998**。
所以这个 run 落盘的最后一个存档是 `model_34998.pt`，
**`model_34999.pt` 从来就不存在**。

而无值守接力脚本 `/tmp/r06_handoff2.sh` 里把续训的起点**写死**成
`--agent.load-checkpoint 'model_34999.pt'`。脚本已经在跑了，此时去改它
是危险的 —— bash 是按需增量读取脚本文件的，改一个正在执行的脚本，
后面的行可能被读到错位。所以选择**不动脚本**，改用一根软链把名字补齐：

```bash
cd logs/rsl_rl/pikachu_v03_velocity/2026-10-09_00-34-34_v03-flat-r06
ln -s model_34998.pt model_34999.pt
```

**为什么这样能work**：`src/mjlab/scripts/train.py:143` 走的是
`get_checkpoint_path(log_root_path, cfg.agent.load_run, cfg.agent.load_checkpoint)`，
它只是 `log_path / run_dir / checkpoint` 拼路径再用 `re.match` 筛；
软链在 `torch.load` 那一层被透明解析，中间没有任何一处会去核对
「文件名里的数字 == 文件里的 `iter` 字段」。

**验证**（不是推断，是日志原文）：

```
[INFO]: Loading model checkpoint from: .../2026-10-09_00-34-34_v03-flat-r06/model_34999.pt
                         Learning iteration 34998/59998
```

从 34998 续上（不是从 0 重启），目标 59998 = 34998 + 25000 ✅。

**⚠️ 留给人看的警告**：这个目录里现在有一个**文件名与内容不符**的文件。
`model_34999.pt` 里装的策略是第 34998 次迭代的。任何以后按文件名做
「最新检查点」推断的脚本，都要知道这一点（`sort -n | tail -1` 会选中它，
但内容等价于 34998，所以实际无害；**有害的是把它当成「34999 迭代」写进报告**）。
本目录的报告抬头因此写明实际来源。

**顺带记下的两个事实**，都属于同一个「文件名 ≠ 内容」家族：

1. 存档节奏是**每 500 迭代**一次，而 run 的终点是 `start + N - 1`，
   所以「跑 N 次迭代」的最后一个存档**不一定**是 `start + N - 1` ——
   它取决于 `start + N - 1` 是否是 500 的倍数。r06：29999 + 5000 − 1 = 34998
   （不是 500 的倍数，最后一个存档点就是 34998）；r04：29999 恰好是终点。
2. `--agent.max_iterations` 在 **resume 时是「追加多少」，不是「总共到多少」**。
